Standard Delay Format, explained

IEC 61523-3:2004 · IEEE Std 1497-2001 (SDF version 4.0)

SDF is a plain-text file that carries timing numbers for a digital circuit: how long a signal takes to travel through each gate and wire, and how much margin flip-flops need. One tool calculates the numbers and writes the file; simulators, timing analysers and layout tools read it.

One line of SDF says: going from pin A to pin Y on this cell, a rising output takes 0.10 / 0.12 / 0.15 time units (best / typical / worst), a falling one 0.07 / 0.09 / 0.11.

// Illustrative file, written for this explainer
(DELAYFILE
  (SDFVERSION "4.0")
  (DESIGN "top")
  (DIVIDER /)            // hierarchy separator
  (TIMESCALE 1ns)
  (CELL (CELLTYPE "AND2") (INSTANCE core/u1)
    (DELAY (ABSOLUTE
      (IOPATH A Y (0.10:0.12:0.15) (0.07:0.09:0.11))))
  )
  (CELL (CELLTYPE "DFF") (INSTANCE core/r1)
    (TIMINGCHECK
      (SETUP D (posedge CK) (0.20::0.25))))
)

The file is a header followed by CELL blocks; each cell names an instance and lists delays or timing checks for it. The header, cell, delay and timing-check constructs are defined in clause 5 of the standard.

How it got here

IEEE Introduction

SDF began at Cadence as a way to pass cell and wire delays from a layout tool into the Verilog-XL simulator. That origin shows: many SDF keywords, such as SETUP and PATHPULSE, mirror constructs in Verilog specify blocks. VHDL uses SDF too, through the VITAL standard.

Version 4.0 changes very little compared with OVI 3.0: it adds a LABEL construct and brings back NETDELAY. The new number mainly marks the move from an industry-consortium document to an IEEE standard. The working group deliberately avoided anything that would break existing files. IEC later adopted the IEEE text unchanged as part 3 of its Delay and power calculation standards series (parts 1 and 2 cover delay and power calculation systems and pre-layout delay calculation for CMOS ASIC libraries).

Reading “shall” and “can”

Clause 3.1

“Shall” marks a mandatory rule; “can” marks an optional feature (which, if used, still has to follow the format). The same “shall” lands differently depending on who you are:

Tool that reads SDFMust enforce the rule and report an error when a file breaks it.
Person reading a fileCan rely on the property being true of any valid file.
Tool or person writing SDFMust produce files that satisfy the rule.

Lexical rules

Clauses 3.2.2 – 3.2.8

Tokens, white space and comments

An SDF file is free-format: tabs, spaces and newlines only separate tokens, so layout and indentation carry no meaning (except inside quoted strings). Two comment styles are allowed:

/* C-style: can span lines, cannot be nested */
(TIMESCALE 1ns)   // C++-style: runs to end of line

Identifiers and escaping

Plain identifiers use letters, digits, _ and $. Any other printable symbol must be prefixed with a backslash to become part of a name; escaping also strips any special meaning the character would have had. This matters because synthesised netlists often contain names with brackets or dots.

The escaped dot is part of the name, not a separator. The header chooses either . or / as the hierarchy divider (clause 5.2.7).

Quoted strings and bit specifications

A quoted string sits between double quotes and may contain spaces and special characters freely; to put a " inside it, escape it as \". Buses are addressed with square brackets: data[3] is a single bit, data[7:0] is a range.

Numbers, values and triples

Clause 3.2.9

Every timing number in SDF is wrapped in parentheses. Inside, you can put a single number, a triple, or nothing at all.

Written asMeaning
(1.5)One number, used for every condition
(1.2:1.5:2.1)Separate min / typ / max values
(:1.5:)Typical only; min and max are not supplied
()“No value here.” A placeholder so later items in a list line up. Tools must leave the existing value alone; it is not zero.

The rvalue and rtriple forms are identical except that they allow negative numbers, which some constructs (for example certain timing checks) need.

Delays with pulse limits

Clause 3.2.9 (delval, delval_list)

A delay value (delval) can carry more than the delay itself. Wrap two or three values in an extra pair of parentheses and they mean:

((0.50) (0.10) (0.30))
   │      │      └─ e-limit: X-limit (pulse error limit)
   │      └──────── r-limit: pulse rejection limit
   └─────────────── the delay

These limits decide what happens to a glitch, a pulse too short to be trusted. The same form works on every delay type: IOPATH, PORT, INTERCONNECT, NETDELAY and DEVICE.

Typical simulator behaviour for pulse limits, following the Verilog pulse-control model SDF was designed around. The detailed rules are in clause 5.4.

How many delays in a list?

A delay entry can list several delvals, one per kind of signal transition. The standard gives meaning to lists of 1, 2, 3, 6 and 12 entries. A list of 4 or 5 is treated as 6 with the missing tail left empty; 7 to 11 is treated as 12 the same way.

The per-transition mapping is defined in clause 5.4.1, which is outside the uploaded excerpt; it is shown here as the standard SDF convention.

Equality operators

Clause 3.2.10

Conditional delays and conditional timing checks compare signal values. Digital signals in SDF can be 0, 1, X (unknown) or Z (high impedance), so there are two families of comparison. Logical equality gives up and returns X when it meets an unknown; case equality treats X and Z as ordinary values and always answers 0 or 1.

Rows are a, columns are b. Green is TRUE (1), grey FALSE (0), red unknown (X).

SDF in the design flow

Clauses 4.1 – 4.4

The point of a shared file format is that every tool works from the same numbers. A layout tool can take the constraints a timing analyser found; a simulator can take the delays extracted after layout. Tools create SDF, read it to update their view of the design, and write it back out.

Several files, one design

Annotation is hierarchical, so a system does not need one giant file. Each chip or block can have its own SDF file, with another file for the wiring between them.

SDF can describe two different kinds of information, and a single file may hold both:

A floorplanner is a good example of a tool that wants both: the current delays and the targets it has to hit.

SDF can also describe the timing environment the design is expected to run in, such as the clock waveform applied at clock pins and when primary inputs arrive (defined in clause 5.7).

Back-annotation, step by step

Clause 4.5, Figure 2

This is the most common use of SDF: compute the real delays of a design once, then feed the same numbers into every analysis tool.

Adapted from Figure 2 of the standard.

Reading the diagram from top to bottom:

  1. Wire delays come from estimation rules early in the project, or from real extracted parasitics once the chip has been routed.
  2. The timing calculator combines those wires with the library’s cell characterisation data and the netlist, and writes the result as SDF.
  3. The analysis tool (a simulator or static timing analyser) loads its own cell models and the netlist, then an annotator reads the SDF file and overwrites the models’ default delays with the calculated ones.
Same file, slightly different answers. Every tool reads identical data, but tools differ in what they can model. A static timing analyser may honour a negative path delay, while a simulator may have to round it up to zero. Small differences in results between tools are therefore expected.
