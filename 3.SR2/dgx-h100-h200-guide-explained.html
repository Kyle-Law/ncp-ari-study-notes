What's in the box

From the chapter Introduction to NVIDIA DGX H100/H200 Systems

The H100 and H200 versions share one chassis, one motherboard and one set of networking. The only difference the guide lists is the GPU: the H200 carries far more memory per GPU, which matters most for large models that would otherwise have to be split across more machines.

Front panel signals

Three indicators on the bezel tell you the machine's state at a glance. The power button's green light changes its blink rate as the system boots.

Solid greenPowered on
Blue ID lightPressed to mark this unit for servicing; a matching light flashes at the rear
Amber fault lightThe system or one of its components has failed

At the back, the motherboard tray repeats the power and ID buttons and adds a button that resets the BMC by hand.

How the parts connect

The key design idea: every GPU gets its own 400 Gb/s network card. GPUs talk to each other inside the box over NVLink through the four NVSwitches, and talk to GPUs in other DGX systems through their dedicated ConnectX-7 card. Four GPUs and their cards sit under each CPU.

Select a GPU to see which network port, Linux interface and RDMA device belongs to it. This mapping matters when you pin jobs or debug a slow link.

Physically, the eight cluster cards are packaged as two "network modules" of four cards each, mounted on an interposer board that links the CPUs on one side to the GPU tray on the other. DensiLink cables run from the cards to the OSFP cages on the rear, and each cable carries two ports, one from each of two cards. That is why each OSFP cage shows two ports belonging to different GPUs.

Network ports

The rear-panel network connections fall into three groups, each with its own job. Select a port to see its PCI address and the names Linux gives it. "Default" is the name you will see out of the box; "optional" is the name after switching the port between InfiniBand and Ethernet.

No cables in the box

The system ships without network cables or adaptors. Which ones work is decided by the ConnectX-7 firmware, and NVIDIA keeps the list of validated cables in the release notes for that firmware.

BMC port lights: the left LED shows link speed (green for 100 Mb/s, amber for 1 Gb/s); the right LED flashes green with traffic.

Storage

Two separate drive sets do two different jobs. The OS sits on a mirrored pair so a single drive failure doesn't take the machine down. The data drives are striped for speed with no redundancy, which is fine because they act as a local cache for datasets that live elsewhere (the cachefilesd daemon in the software stack manages this).

After a fresh install or re-image, the OS mirror rebuilds itself for up to an hour. Performance can dip and nvsm show health will warn about re-syncing until it finishes; sudo nvsm show volumes shows progress.

Power and redundancy

From the chapters on hardware and Managing Power Capping

Six 3.3 kW supplies feed a system that can draw up to 10.2 kW. They're arranged as 4+2: four can carry the full load and two are spares. Each supply needs 200–240 V AC at 16 A, and must use the six locking C19/C20 cords NVIDIA ships with the system.

Try it: select supplies to take them offline and see what the guide says happens.

10.2 kW peak draw
0 kW19.8 kW
Never cut power to a running system

Pulling cords or switching off the PDU while the OS is running can damage components. Shut down from the OS, with a short press of the power button, or with Graceful Shutdown in the BMC, and wait until it is fully off before any maintenance. Don't run the system with supply bays left empty.

Who decides each GPU's power limit

Three sources can set a GPU power limit. The GPU's own power-management unit always obeys whichever is lowest.

For an N+N setup (two independent power feeds, each able to run the box), the guide says to turn on the system-level power-capping feature so total consumption stays limited. Over IPMI that means reading the current limit and writing a new one. The limit comes back as two little-endian bytes: a reply of c8 32 means 0x32C8, or 13,000 W. Anything above 12,000 means capping is off, which is the default from firmware 24.07.1 onward.

# read the current system power limit
ipmitool raw 0x3c 0x80 0x05
# set a 12 kW budget (0x2EE0 = 12000, sent low byte first)
ipmitool raw 0x3c 0x81 0x05 0xE0 0x2E

NVIDIA's page prints the second command as x3c; 0x3c is shown here to match the read command. The same controls are also available through Redfish.

Getting to a console

From the chapter Connecting to DGX H100/H200

There are three ways in. The first two give you the machine's own screen, so they work before any OS setup. SSH only works once first-boot setup has configured the network.

Change the BMC's factory login before it touches a shared network

Until first-boot setup runs, the BMC accepts the factory default credentials, which are published in the guide. First-boot replaces them: the BMC then uses the administrator username you create plus a separate BMC password. NVIDIA also recommends keeping the BMC on an isolated management network, a firewalled subnet, or at least its own VLAN.

The 172.17.x.x trap

Docker on the DGX uses 172.17.x.x for containers by default. If your office or data-center network also uses that range, you won't be able to reach the system over the network, so connect directly to the console and change Docker's address range first (covered in the DGX OS 6 User Guide).

First boot to production

From First Boot Setup and Quickstart and Basic Operation

NVIDIA's installers normally do the first steps on site. The guide documents them anyway because you'll repeat them whenever the system is re-imaged. Hollow markers are optional or situational steps.

  1. Register the system

    Follow the Entitlement Certification email from the purchase. It unlocks the support portal, software updates and an NGC account for NVIDIA's container registry.

  2. Connect to the console

    Directly or through the BMC's remote KVM, as shown above.

  3. Power on

    With the physical button or from the BMC. After the login prompt appears, give it up to a minute of idle time so every component finishes starting.

  4. Run the first-boot wizard

    Accept the EULAs, choose language and locale, create the administrator account (used for the OS, the BMC and the GRUB boot loader), and configure the primary network interface. Encrypting the root file system is offered here too.

  5. Let the OS mirror rebuild

    Up to an hour of reduced performance while RAID 1 syncs.

  6. Update DGX OS

    Pulls in security fixes; Ubuntu's security notices list which CVEs updates resolve.

  7. Enable the SRP daemon only for RDMA over InfiniBand

    sudo systemctl enable srp_daemon.service
sudo systemctl enable srptools.service

  8. Quick health check

    Over SSH, confirm everything reports Healthy, Docker is present, and a container can see all eight GPUs.

    sudo nvsm show health
sudo docker --version
sudo docker run --gpus all --rm nvcr.io/nvidia/cuda:12.1.1-base-ubuntu22.04 nvidia-smi

  9. Pre-flight stress test

    Loads the GPUs, CPUs, memory and storage for about 20 minutes. NVIDIA recommends it before production and after any servicing.

    sudo nvsm stress-test --force

Daily operation

Running GPU containers

Work on a DGX is meant to run in containers, mostly NVIDIA's optimised images from NGC. Docker 20.10.18 and later understand GPUs natively, so you pick GPUs with the --gpus flag:

sudo docker run --gpus all ...              # every GPU
sudo docker run --gpus 2 ...                # any two GPUs
sudo docker run --gpus '"device=1,2"' ...   # GPUs 1 and 2 specifically

The older nvidia-docker2 runtime still works on DGX OS 6 but is deprecated. If you make it Docker's default runtime, image builds may get tuned only for the GPU they were built on unless the build declares its target architectures.

CPU security mitigations: a speed trade-off

DGX OS ships with protections against CPU side-channel attacks (Spectre-style bugs). They cost some performance in AI workloads. If your cluster already defends against these attacks at another layer, you can turn them off per node with one package and turn them back on by removing it. Each change needs a reboot.

# check: "Mitigation:" lines = on, "Vulnerable" lines = off
cat /sys/devices/system/cpu/vulnerabilities/*

# turn mitigations off, then reboot
sudo apt install nv-mitigations-off -y

# turn them back on, then reboot
sudo apt purge nv-mitigations-off
