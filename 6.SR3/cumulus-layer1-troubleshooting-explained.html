01The big picture

Layer 1 is the physical layer: the transceiver module, the cable or fiber, the port on the switch, and the electrical or optical signal between them. If Layer 1 is unhealthy, nothing above it (VLANs, routing, BGP) can work reliably, so it's the first thing to rule out when a link misbehaves.

The rest of this guide is background you need to diagnose confidently (sections 2–8), how to read the diagnostic output (9), and a problem-by-problem playbook (10–15).

02Modules & form factors

Two standards bodies define this world: IEEE 802.3 specifies the Ethernet technologies and link characteristics, while the SFF MSA specs define how SFP/QSFP modules are physically built and how their management memory is laid out (SFF-8472 for SFP, SFF-8636 for QSFP, plus the OSFP MSA).

Each pluggable carries an EEPROM describing itself. Byte 0 of that memory map is the identifier, which tells the switch what shape of module it is. ethtool -m swpN decodes it.

04Active vs. passive, and compliance codes

If the switch thinks an active module is passive (or vice versa) it tunes the port wrongly, which can hurt signal integrity. That's why the compliance code matters.

Decode a compliance code

The compliance code (also called Ethernet type, ethmode type or interface type) is read from the module EEPROM and tells the port what technology it's driving. It reads as speed + BASE + media + lane count.

Some modules are old, proprietary or oddly coded and aren't recognized correctly. On NVIDIA switches, the port firmware automatically overrides known supported modules to the right compliance code.

05DDM/DOM: telemetry from optics

Digital Diagnostic / Optical Monitoring is an optional feature on optical transceivers that reports temperature, voltage, laser bias current, and — most usefully — TX optical power (what the laser emits) and RX optical power (what arrives). Readings are typically trustworthy to roughly ±10%. Show them with nv show platform transceiver swpN or ethtool -m swpN.

The golden rules

Autodetect: what happens when autoneg is ON but the media can't negotiate

Because vendors let you enable autoneg on any port, Cumulus Linux handles the unsupported case with autodetect: the port cycles through plausible autoneg/speed/FEC combinations for that port + module until the link comes up. It isn't separately configurable — it's simply always active when autoneg is ON (the default on NVIDIA platforms). It's purely local; the neighbor is assumed to be forced, or running something equivalent.

07Forward error correction (FEC)

FEC adds redundant bits so the receiver can repair a limited number of bit errors itself. The IEEE target is a bit error rate (BER) of 10−12 — one bad bit per trillion. At 25G per lane and above, some cables can't hit that without FEC.

Both ends must run the same FEC algorithm or the link stays down. If the signal path looks healthy on both sides but the link won't come up, suspect an autoneg or FEC mismatch first.

FEC helper

Configured and operational FEC can legitimately differ. For example, configured Auto may show operational RS once negotiated, while configured RS on a down link shows operational None. l1-show displays both.

08Signal integrity: link states & eyes

The whole goal of Layer 1 is that bits sent on one side arrive intact on the other. The switch reports a ladder of states — each rung depends on the one below. Find the highest rung that's healthy and you know where to look.

Local fault vs. remote fault

The RX fault field tells you which direction is broken. Toggle the scenario:

Eyes and grades

Overlay every 1→0 and 0→1 transition on an oscilloscope and you get the eye pattern in the hero at the top of this page. A wide-open eye means 1s and 0s are easy to tell apart; a closing eye means bits get misread. One misread bit corrupts the frame's checksum (an FCS error) and the whole packet is lost — unless FEC catches it first.

NVIDIA switches report eye height (mV) and a grade. For NRZ links below 100G, a grade under about 4000 suggests errors or instability may appear — though FEC may still clean it up.
PAM4 (50G lanes) stacks three small eyes, so measurements are much lower by nature. FEC is mandatory there. Eyes aren't measured on fixed copper ports or on down links.

10The troubleshooting method

The guide's approach is essentially the scientific method applied to cabling: characterize the symptom, find the lowest-level indicator that shows it, then change one thing at a time while watching that indicator.

Problem classes the guide covers: link down or flapping · physical errors (not the same as drops, which are L2/L3 forwarding issues) · signal integrity · MTU mismatch · high-power module · I2C bus.

11Down or flapping links

Symptoms include: l1-show reporting Kernel and Hardware both Down; ip link show showing NO-CARRIER (a healthy link shows LOWER_UP) or changing every second or two; carrier up/down entries in /var/log/linkstate; and no LLDP from the neighbor.

Checklist — run on both ends, top to bottom

  • Right port, right module? Vendor name and part number match what's physically installed.
  • Right type? Module type matches the link technology (a 100G DAC should read as 100G-CR4), and the far end agrees on the Ethernet type (check vendor docs if it isn't Cumulus).
  • Admin Up? Port configured and enabled.
  • Speed, autoneg and FEC consistent with the neighbor and the rules in sections 6–7.
  • MTU matches — won't keep the link down, but will break forwarding.
  • Operational state: kernel and hardware in sync? Speed Unknown! with autoneg on usually just means down. Operational FEC is None whenever the link is down.
  • TX/RX power in range (optics only) — and check every lane on QSFP; one dead lane kills the whole link.
  • LLDP neighbor is who you expect (blank when down).
  • Troubleshooting Info — the firmware's own diagnosis. Often the fastest first look.

12Physical errors & signal integrity

Physical errors come from marginal signal integrity or from missing the FEC a given cable type requires. Signal quality maps onto link behavior like this:

Uncorrected errors: ethtool -S swpN | grep Errors. With FEC on, these count only what FEC couldn't fix.
Errors FEC corrected (NVIDIA): sudo l1-show swpN --pcs-errors.

Counters also bump during link up/down transitions, so watch whether they keep incrementing over time rather than trusting a single snapshot. /var/log/linkstate records historical transitions. And rarely, a module misidentified as active vs. passive can itself cause signal-integrity trouble.

13MTU mismatches

An MTU mismatch generally leaves the link up — the clue is higher-layer breakage like OSPF adjacencies failing or non-fragmentable packets vanishing. Compare the MTU in l1-show's Configured State with the neighbor's. Vendors sometimes count MTU a few bytes differently (headers included or not), so check the neighbor's documentation before assuming a true mismatch.

14High-power modules

Modules declare a power class; ones that need more than the default must request it, and the switch grants it only if that port supports it. Long-reach lasers are the usual high-power customers.

To see whether a module asked for high power and got it, read the Extended identifier description lines in sudo ethtool -m swpN. Ignore the generic "max power consumption" line for high-power modules; the line that matters states the requested wattage and whether "High Power Class (> 3.5 W)" is enabled or not enabled.

15I2C bus lockups

I2C is the slow management bus the switch CPU uses to talk to modules, fans and power supplies. A defective module (most often a cheap one, though any can fail) can hang the bus. Data traffic may keep flowing for a while, but modules can be misconfigured, links fail or errors rise, and at worst the switch reboots or freezes. This is a hardware problem — not a Cumulus software bug.

Signs: modules disappear from l1-show/ethtool -m; repeated or bursty smbus, i2c or EEPROM read errors in sudo tail -F /var/log/syslog. Once one module locks the bus, others misbehave too, hiding the culprit. Fixes can hold for hours or months before recurring — so act decisively.

Recovery options: likelihood of clearing vs. traffic impact

If it keeps coming back

Escalate systematically: remove half the modules and power-cycle (binary search); if errors persist with no modules, remove PSUs and fans one at a time between power cycles; if it still fails with everything isolated, replace the switch. If the switch recovers but the culprit is unknown, first replace any module with a syslog history of errors or past trouble — and if needed, replace all modules. NVIDIA Enterprise Support is the final escalation.
